## D-01 M 静音键仅在 PLAYING 状态生效【严重度：P1】

### 需求依据

[需求文档 §6.2 FR-INPUT](../specs/2026-11-23-flappybird-design.md) 明确写道：

> `M`：静音开关（**任意状态生效**，屏幕角落显示 `MUTE` 提示 1.5s）

### 复现步骤

```powershell
cd "E:\AI study\homework\FlappyBird"
& .venv\Scripts\python.exe -c "
import os,sys
os.environ['SDL_VIDEODRIVER']='dummy'; os.environ['SDL_AUDIODRIVER']='dummy'
sys.path.insert(0,'.')
import pygame
from src.game import Game
from src.states.base import StateName

for setup, label in [
    (lambda g: None, 'READY'),
    (lambda g: g.state.handle_key(pygame.K_p), 'PAUSED'),
    (lambda g: (g.state.pipes.clear(), setattr(g.state.bird,'y',400), g.state.update(1/60)), 'DYING'),
    (lambda g: g.set_state(StateName.GAMEOVER), 'GAMEOVER'),
]:
    g = Game(rng_seed=0, scale=1)
    if label != 'READY': g.state.handle_key(pygame.K_SPACE)
    setup(g)
    before = g.audio.muted
    g.state.handle_key(pygame.K_m)
    print(f'{label:9s} muted {before} -> {g.audio.muted} badge={g.mute_badge_t}')
"
```

### 实际结果

```text
READY     muted False -> False badge=0.0     ← 无反应
PLAYING   muted False -> True  badge=1.5     ← 正常
PAUSED    muted False -> False badge=0.0     ← 无反应
DYING     muted False -> False badge=0.0     ← 无反应
GAMEOVER  muted False -> False badge=0.0     ← 无反应
```

### 预期结果

5 个状态下按 M 都应切换静音并显示 1.5 秒角标。

### 根因

`M` 键的分支只写在 `src/states/playing.py` 的 `handle_key` 里：

```python
# src/states/playing.py
elif key == pygame.K_m:
    self.game.audio.toggle_mute()
    self.game.mute_badge_t = c.MUTE_BADGE_SECONDS
```

其余四个状态的 `handle_key` 都没有处理 `K_m`。而 `Game.handle_events` 是把按键直接转发给当前状态的：

```python
# src/game.py handle_events
self.state.handle_key(event.key)
```

### 影响范围

- **用户可感知**：READY 屏（占玩家第一印象）按 M 无效，玩家会以为静音坏了；暂停时想静音必须"先恢复→再按 M→再暂停"，体验割裂。
- **需求符合性**：直接违反 FR-INPUT 的明确条款，属"需求未落地"。
- **数据影响**：无，不涉及存档。

### 修复建议（按侵入性从低到高）

**方案 A（推荐，2 行）**：把全局键提到 `Game.handle_events` 层，在任何状态前拦截：

```python
# src/game.py handle_events, KEYDOWN 分支
if event.key == pygame.K_ESCAPE:
    return False
if event.key == pygame.K_m:                      # 全局键：任意状态生效
    self.audio.toggle_mute()
    self.mute_badge_t = c.MUTE_BADGE_SECONDS
    continue                                  # 不再下发给状态，避免重复处理
self.state.handle_key(event.key)
```

同时删除 `playing.py` 里的 `K_m` 分支，避免双击切换两次。

**方案 B（最小改动，4 行）**：在 `State` 基类的 `handle_key` 里处理 `K_m`，子类调用 `super().handle_key(key)`。

**回归测试**：新增参数化用例，5 状态 × M 键，断言 `muted` 翻转且 `mute_badge_t == 1.5`。

## D-02 静音状态与角标在重开后未重置【严重度：P3】

### 复现步骤

```python
g = Game(rng_seed=0, scale=1)
g.state.handle_key(pygame.K_SPACE)
g.state.handle_key(pygame.K_m)        # 静音，角标 1.5
# ... 死亡 -> GAMEOVER -> 按 R 重开
print(g.mute_badge_t)                # 实际 1.5，期望 0
```

### 预期 vs 实际

| 项 | 预期 | 实际 |
|---|---|---|
| `mute_badge_t` | 重开后归零 | 保持 1.5 |
| `audio.muted` | 保持（静音是用户偏好，应跨局保留） | 保持 ✅ |

### 根因

`Game.reset_round()` 只重置分数、stage、管道、背景、地面，未清理 UI 计时器：

```python
def reset_round(self):
    self.score = 0
    self.stage = 0
    self.pipes.clear()
    self.background.set_stage(0)
    self.ground.reset()
    # 缺 self.mute_badge_t = 0.0
```

### 影响范围

重开瞬间底部可能残留 "MUTE" 角标（最长 1.5 秒），属视觉瑕疵；不改变静音实际状态（这一点是正确的）。

### 修复建议

在 `reset_round` 增加一行 `self.mute_badge_t = 0.0`。**注意不要重置 `audio.muted`**——那是用户偏好，跨局保留才合理。

## D-03 超范围分数可写入存档，导致最高分被静默抹除【严重度：P2】

### 复现步骤

```python
from src.score_store import HighScoreStore
import tempfile, pathlib
d = pathlib.Path(tempfile.mkdtemp())
s = HighScoreStore(d / "h.json")
print(s.save_if_better(10**6))       # 返回 1000000，已写入文件
print(HighScoreStore(d / "h.json").load())   # 返回 0  ← 下次启动最高分没了
```

### 实际结果

```text
1000000
0
```

### 预期结果

按 Spec FR-STORE-2「读取时校验 `0 <= best < 10^6`」，写入侧应做**同样的**校验：要么拒绝写入并返回原 best，要么裁剪到上限。

### 根因

`load()` 有上界校验，`save_if_better()` 没有，两侧不对称：

```python
# src/score_store.py
_MAX_REASONABLE = 10**6

def load(self) -> int:
    ...
    if not 0 <= value < _MAX_REASONABLE:   # ← 读时校验
        return 0
    return value

def save_if_better(self, score: int) -> int:
    if score <= self.best:                  # ← 写时不校验
        return self.best
    self.best = score                       # ← 可写入 10^6 以上
    ...
```

### 影响范围

- **触发条件**：分数 ≥ 1,000,000 或分数被外部设为负数/超大值。正常游玩几乎不可能达到，属**防御性缺陷**。
- **后果**：写进去的值读不回来 → 玩家下次启动最高分显示 0，**表现为"最高分丢失"**，且无任何报错日志。
- **数据影响**：可能丢失用户历史最高分（虽然概率极低）。

### 修复建议

```python
def save_if_better(self, score: int) -> int:
    try:
        score = int(score)
    except (TypeError, ValueError):
        return self.best
    if not 0 <= score < _MAX_REASONABLE:      # 与 load 对称
        return self.best
    if score <= self.best:
        return self.best
    ...
```

**回归测试**：`save_if_better(10**6)` 返回旧 best 且文件不更新；`load()` 与之保持一致。

## D-04 GAMEOVER 画面丢失管道，导致结算时画面突变【严重度：P2】

### 复现步骤

死亡后用同一批管道分别渲染 DYING 与 GAMEOVER：

```python
from src.states.dying import DyingState
from src.states.gameover import GameOverState
pipes = [PipePair(x=200.0, center=250.0, gap=110.0, speed=0.0)]
dying  = DyingState(g, bird, pipes, g.ground)
gover  = GameOverState(g); gover.enter()
# 对比两张图上 y<400 区域的差异
```

### 实际结果

```text
DYING vs GAMEOVER 上半屏差异像素: 21527
```

两张图的管道区域完全不同——GAMEOVER 把管道全丢了。

### 预期结果

原版 FlappyBird 在结算面板出现时**保留现场**（管道、小鸟停在地面），只有地面停止滚动。当前实现让画面在 DYING→GAMEOVER 的一瞬间"管道全部消失"，观感突兀。

### 根因

`GameOverState.draw` 只画了背景与地面，没有画管道与小鸟：

```python
# src/states/gameover.py
def draw(self, surface):
    self.game.background.draw(surface)
    self.game.ground.draw(surface)     # ← 没有 pipes，也没有 bird
    ...
```

而 `DyingState.draw` 是画了管道的。所以状态一换，管道消失。

### 影响范围

- **用户可感知**：结算瞬间画面"跳变"，玩家会明显察觉。
- **掩盖问题**：玩家看不到自己撞在哪根管道上，降低"我为什么死"的反馈质量。
- **不影响**：分数、最高分、重开逻辑均正常。

### 修复建议

在 `GameOverState.enter` 里保存现场引用，`draw` 时还原：

```python
def enter(self):
    self.final_score = self.game.score
    self.best = self.game.best

def draw(self, surface):
    self.game.background.draw(surface)
    for pipe in self.game.pipes:                    # 补：保留管道现场
        pipe.draw(surface, self.game.assets)
    self.game.ground.draw(surface)                  # 地面画在管道之后（同 PLAYING）
    ...
```

注意 `Game.pipes` 在 DYING 期间没有被清理（`.reset_round` 只在重开时调用），所以直接引用即可；**小鸟不必画**（它已落地，视觉上可由管道交代）。

**证据截图**：`build/testing/D08_dying_pipes.png` 与 `build/testing/D08_gameover_nopipes.png` 对比。

## D-05 ~~分数数字与最靠顶的管道存在 4 行视觉重叠~~【已撤回：非缺陷】

### 复现步骤

构造最靠顶的管道（`center = PIPE_MARGIN + MIN_GAP/2 = 88`），让一根管道位于屏幕中部，同时分数为 88（数字条 x 范围 119..167）：

```python
pair = PipePair(x=130.0, center=c.PIPE_MARGIN + c.MIN_GAP/2, gap=c.MIN_GAP, speed=0.0)
pair.draw(canvas, assets)
```

### 实际结果

```text
分数区间   x: 119..167   y: 44..79
上管区间   x: 130..181   y:  0..48
水平重叠   x: 130..167
垂直重叠   y: 44..47  =>  4 行
```

见 `build/testing/D05_score_over_pipe.png`：数字 "88" 的上沿被管道盖住。

### 预期结果

分数应始终完整可读。Spec §9.2 规定"分数永远在顶部中线"，隐含要求不被遮挡。

### 根因

两个常量各自独立、没有相互约束：

```python
# src/config.py
PIPE_MARGIN = 48        # 缝隙中心离顶部的最小距离 → 上管最高只能到 y=48
SCORE_Y = 44            # 分数数字顶部
# 数字高 36 → 占据 44..79，与 0..48 的管道重叠 4 行
```

### ⚠ 本条已在修复阶段撤回（原判定有误）

**原判定**：分数与管道矩形有 4 行几何重叠，判为"视觉遮挡"。

**复核结论**：**不构成缺陷**。逐像素采样重叠行 y=46：

```text
y=46 颜色分布: {白色(255,255,255) 36, 深描边(20,24,28) 11, INK(84,56,71) 2}
重叠行内 管道绿色像素 = 0
```

原因：`PlayingState.draw` 的绘制顺序是 **背景 → 管道 → 小鸟 → 地面 → HUD 分数**，分数在管道**之后**绘制，因此始终在最上层。所谓"重叠"只是**几何包围盒相交**，实际画面中数字完整可见，只是背景从天空蓝变成了管道绿。

白色数字 + 深色描边在管道绿（#84AA45 系）上对比度充足，符合 Spec §9.3「白字 + 2px INK 描边，保证在两种天空色上都可读」的要求。

**教训**：矩形相交 ≠ 视觉遮挡。判断遮挡必须**按绘制顺序**和**实际像素**验证，不能只看几何。

**若仍想消除该现象**（可选优化，非必修）：把 `PIPE_MARGIN` 提到 88 可让管道完全避开分数带，但会把缝隙中心可用范围从 88..312 收窄为 128..272（-25%），需重跑 `tune_sim.py` 与 `test_tuning_invariant.py`。**当前决定：不做**。

## D-06 最高分为 0 时结束面板 BEST 行下方空白【严重度：P2】

### 复现步骤

首局结束（从未得分）：

```python
g = Game(rng_seed=0, scale=1); g.score = 3; g.best = 0
g.set_state(StateName.GAMEOVER)
g.state.draw(canvas)     # 观察 BEST 标签下方
```

### 实际结果

见 `build/testing/D06_gameover_best0.png`：`BEST` 标签下方**完全空白**，没有数字。

像素证据：

```text
draw_number(0) -> 像素数 0      ← 什么都不画
draw_number(8) -> 像素数 856
GAMEOVER best=0 vs best=8 的 BEST 区差异 = 856  ← 确认 0 时不画
```

### 预期结果

应显示 `BEST 0`。玩家首次游玩（还没破纪录）时，界面给出"BEST 后面什么都没有"会造成困惑。

### 根因

`Hud.draw_number` 对 `value <= 0` 直接 return：

```python
def draw_number(self, surface, value, y, x_center=None):
    if value <= 0:
        return          # ← 为"PLAYING 时 0 分不显示"设计的规则
```

这条规则对 **PLAYING 的实时分数**是对的（Spec FR-SCORE-2「分数为 0 时不显示」），但对 **GAMEOVER 的 BEST 行**不适用——那里必须显示数字。

### 影响范围

- **触发条件**：玩家首次启动、还没拿到任何分数就死亡（很常见，新手第一次玩几乎必然 0 分）。
- **用户可感知**：结算面板少一行数字，观感像 bug。
- **不影响**：存档、重开、最高分逻辑。

### 修复建议

给 `draw_number` 加 `allow_zero: bool = False` 参数，GAMEOVER 调用时传 `True`：

```python
# src/hud.py
def draw_number(self, surface, value, y, x_center=None, allow_zero=False):
    if value <= 0 and not allow_zero:
        return
    value = max(0, value)              # 负数统一显示 0
    ...

# src/states/gameover.py
hud.draw_number(surface, self.best, c.BEST_PANEL_Y, allow_zero=True)
hud.draw_number(surface, self.final_score, c.SCORE_PANEL_Y, allow_zero=True)
```

**注意**：本局分数为 0 时也应显示 `0`（同样理由）。当前 `SCORE_PANEL_Y` 那行也有同样问题，复现方式：首局 0 分结束时整块面板两个数字都没有。

**回归测试**：GAMEOVER 状态下 `best=0`、`score=0` 时，两个数字区的非空像素数应 > 0。

## D-07 注释与实现不符：DYING 的 hit 音效实际由 PLAYING 播放【严重度：P3】

### 位置

`src/states/dying.py` 与 `src/states/playing.py`

### 现象

`dying.py` 的类注释写道"撞击阶段"，但 `hit` 音效实际在 `playing.py` 里播放：

```python
# src/states/playing.py
if is_dead(...):
    self.game.audio.play("hit")      # ← hit 在这里
    self.game.set_state(StateName.DYING, DyingState(...))
```

而 `dying.py` 只负责 `die`（落地音）。

### 影响范围

纯可维护性。新维护者按状态机直觉会去 `dying.py` 找撞击音，浪费排查时间。**无功能影响**。

### 修复建议

二选一：① 在 `dying.py` 注释里明确"撞击音由 PLAYING 在迁移前播放"；② 把 `hit` 移到 `DyingState.enter()`，让每个状态自管音效（语义更内聚）。

方案 ② 更符合"状态自治"，但需注意 `enter()` 在 Game 层调用时机——当前 `set_state(name, instance)` 挂载既有实例时**不调用 enter()**，需确认迁移路径统一。

## D-08 src/smoke.py 属测试工具却位于生产包【严重度：P3】

### 现象

`src/` 下有 22 个 `.py`，其中 `smoke.py` 是**无头截图脚本的宿主模块**，服务对象是 `scripts/smoke_run.py`，不被任何生产代码引用：

```text
smoke.py 是否被生产代码引用: False
```

### 影响范围

## D-09 Game.state_name 依赖类属性兜底【严重度：P3】

## D-13 用系统 Python 直接运行会启动失败【严重度：P1，用户实际反馈】

### 现象

用户按最自然的方式运行：

```powershell
(base) PS E:\AI study> python -u "e:\AI study\homework\FlappyBird\main.py"
依赖缺失：No module named 'pygame'
请先执行：uv venv .venv && uv pip install --python .venv\Scripts\python.exe -r requirements.txt
```

游戏**完全无法启动**。这不是代码 bug，而是**开箱可用性缺陷**。

### 根因

用户的 `python` 指向系统解释器，与项目虚拟环境是两套环境：

```text
用户运行的解释器: C:\Users\Lenovo\AppData\Local\Microsoft\WindowsApps\python.exe   → 无 pygame
项目虚拟环境:     .venv\Scripts\python.exe (Python 3.12.15)                          → pygame 2.6.1 ✓
```

原实现只打印一段**需要用户手动复制执行**的命令。对作业交付/送给别人玩而言不可接受——用户只想要"双击就能玩"。

### 影响范围

- **用户可感知**：100% 阻断，游戏完全无法启动。
- **触发频率**：任何未激活 .venv 的环境（IDE 直接 Run、双击、命令行、他人机器）都会触发。
- **严重性判定**：虽然不损坏数据，但**核心功能完全不可用**，按 P1 处理。

### 修复方式（四层兜底）

**第 1 层：自动重定向到 .venv**（主路径）

`main.py` 在 import pygame 之前先调用 `src/launcher.py::ensure_environment()`：

```python
# main.py
from src.launcher import ensure_environment, project_root
handled = ensure_environment(project_root(), sys.argv[1:])
if handled is not None:
    return handled
```

决策逻辑是纯函数 `decide_startup_action()`，6 种组合全部有单测：

| 当前解释器 | .venv 存在 | 守卫已设 | 动作 |
|---|---|---|---|
| 有 pygame | — | — | `run` 直接跑 |
| 无 pygame | 是 | 否 | `reexec` 切换到 .venv |
| 无 pygame | 否 | 否 | `create_venv` 自动建环境 |
| 无 pygame | 是/否 | 是 | `abort` 不再循环 |
| 无 requirements.txt | — | — | `abort` |

**第 2 层：自动创建环境**

`.venv` 不存在时，依次尝试：
1. `uv venv .venv --python 3.12` + `uv pip install ...`（首选，快）
2. `python -m venv .venv` + `.venv\Scripts\python -m pip install ...`（无 uv 时兜底）

**第 3 层：可复制粘贴的绝对路径指令**

全部自动尝试失败时，打印**带绝对路径**的命令（不再是含糊的 `cd 项目目录`），用户可直接粘贴：

```text
cd "E:\AI study\homework\FlappyBird"
uv venv .venv
uv pip install --python "E:\...\.venv\Scripts\python.exe" -r "E:\...\requirements.txt"
"E:\...\.venv\Scripts\python.exe" "E:\...\main.py"

若没有 uv，可改用：
python -m venv .venv
...
```

**第 4 层：无限重启守卫**

用环境变量 `FLAPPYBIRD_LAUNCHER_REEXEC=1` 标记"已重启过"。若在 .venv 里仍然缺 pygame，直接 abort 而非自我重启——避免进程无限 fork。

### 附带修复的一个逻辑 bug

初版守卫写成 `if has_pygame and not force_no_pygame: return "run"`，导致**重启后的子进程**（`force_no_pygame=True`，但实际已有 pygame）被误判为"仍然没 pygame"而 abort。

这个 bug 是被端到端测试抓到的，单测覆盖不到（因为单测只校验决策函数的输入输出组合，没有模拟真实的重启链路）。**再次说明端到端测试的价值。**
